# サーフボード・フィール提案アプリ 仕様書

## コンセプト

浮力計算ベースの従来型ボードセレクター(if文的ロジック)ではなく、**「言語化できないフィーリングを言語化し、それに合うボードを提案する」**アプリ。

- 判断の主語は数値ではなく「フィール」。浮力・長さ・厚みは結果として出す
- 「浮力が余ってる=悪」ではなく「浮力の余りはグライドの原資」と再定義する
- ボリューム至上主義(全員がパフォーマンス量産系に収束する商業的世界観)からの脱却
- LLM前提だからこそ作れるアプリ。従来のボードセレクターには不可能な領域

## コア機能1: フィールの語彙化エンジン

### フィール軸(6項目)

| 軸 | 説明 | 対応するボード世界 |
|---|---|---|
| グライド感 | パドル一掻きで滑り出す、波のパワーを溜めて走る感覚 | グライダー、シングルフィン |
| フロー感 | ターンとターンが途切れない、線がつながる感覚 | ツイン、ミッドレングス |
| ホールド感 | ハイラインを張ってレールが噛んでいる安心感 | ピンテール、シングルフィン |
| ルース感 | テールが抜ける遊び、ドリフトの気持ちよさ | フィッシュ、ツイン |
| 反応性 | 足元で即座に向きが変わるキレ | パフォーマンス系 |
| 静けさ | 板の上で何もしなくていい感覚 | ログ、グライダー |

### 入力設計

- メイン入力は身長体重ではなく、**「波乗り体験の中で一番気持ちよかった瞬間」の自由記述**
- LLMがその記述をフィール軸6項目のベクトルに翻訳する
- 例: 「頭サイズのハイラインをただ走ってるだけで最高だった」→ グライド◎ ホールド◎ 反応性不要 → 浮力オーバー上等のミッド〜グライダー
- 補助入力(体重、スキル、ホームポイントの波質、波サイズ、入水頻度)は補正用として後段で使う

### 出力設計

- ボードタイプ(フィッシュ / ツイン / ミッドレングス / パフォーマンス / グライダー / シングルフィンログ 等)
- フィンセットアップと選定理由
- 推奨ボリューム(L)・長さ・幅・厚みのレンジ(あくまで結果として提示)
- 「なぜこの板があなたのフィールに合うか」の言語化された説明
- 第2候補と条件が変わったときの使い分け

## コア機能2: 語彙の蒸留アーキテクチャ(RAGではない)

### 基本方針

元記事をそのまま格納・引用するRAGではなく、**「語彙の蒸留」**方式を採用する。

- 元記事は素材であって出力物ではない
- ストレージに残るのは元テキストではなく、**抽出済みのフィール語彙辞書+ボード特性マッピング**
- 出力時は辞書を参照してLLMが自分の言葉で生成するため、元記事の表現がそのまま出ない構造にする
- 事実やアイディア(ロッカーと挙動の因果、感覚の呼び名)は著作権の保護対象外。保護されるのは具体的な文章表現。表現の丸写しを構造上不可能にすることで権利面のリスクを最小化
- 元ソースは蒸留処理後に破棄できる

### 蒸留パイプライン

```
収集(スクレイプ / YouTube字幕取得)
  ↓
チャンク分割
  ↓
抽出プロンプト(Claude APIバッチ処理)
  - フィール表現の言い回しを抽出
  - それが指すボード特性とペア化
  - フィール軸へのスコアリング
  ↓
JSON語彙辞書に蓄積
  例: { expression: "rail engagement through the mid-face",
        feel_axes: { glide: 0.8, hold: 0.9, response: 0.2, ... },
        board_traits: ["pintail", "mid-length", "single fin"],
        source: "出典メモ(内部管理用)" }
  ↓
アプリは辞書のみ参照(元記事は破棄)
```

### 蒸留方式の副次的メリット

- 生記事RAGよりノイズが減る(記事の8割は旅行記や選手の話などフィールと無関係)
- 蒸留段階でフィール語彙だけ濃縮するため、検索・生成の精度が上がる

## コーパス候補(フィール語彙の濃いソース)

- **Needessentials** — ブログ+YouTube。Ryan Scanlonの語り。脱・商業パフォーマンス路線でフィール語彙の宝庫
- **Stab Magazine** — ボードレビュー(Stab in the Dark等)の言語化が秀逸
- **The Surfer's Journal** — 長文エッセイ系。グライドやフローの哲学的語彙
- **Swaylock's(シェイパーフォーラム)** — ロッカー×レール×フィンの因果を語る生データ
- **YouTube字幕** — Needessentials、Stab、シェイパー系チャンネル(JS、CIのデザイントーク)。yt-dlpで取得可能

## マッチングロジック

1. ユーザーの自由記述 → LLMがフィール軸ベクトルに翻訳
2. 語彙辞書内の表現をembedding済みにしておき、ベクトル近傍検索(ローカルならChromaが軽い)
3. ヒットした語彙群に紐づくボード特性を集計
4. 補助入力(体格・スキル・波質)で浮力・寸法レンジを補正
5. LLMが辞書の語彙を使って「自分の言葉で」提案文を生成

## 技術スタック(想定)

- **蒸留バッチ**: Python + Claude API(バッチ処理)、yt-dlp(字幕収集)
- **辞書ストア**: JSON + Chroma(ローカルベクトルDB)
- **アプリ本体**: まずCLI or シンプルなWebフォーム(React)。質問に答えると結果が出る形
- **生成**: Claude API(辞書参照+提案文生成)

## MVPロードマップ

1. **Phase 1**: Needessentials のYouTube字幕のみで蒸留パイプラインを構築(量より質、フィール語彙が濃い単一ソースで検証)
2. **Phase 2**: 自由記述→フィール軸翻訳→辞書マッチング→提案生成の一気通貫をCLIで動かす
3. **Phase 3**: 効果を見てコーパス拡張(Stab、Surfer's Journal、Swaylock's)
4. **Phase 4**: Webフォーム化、第2候補・使い分け提案の追加

## 設計思想メモ

- 数値(浮力)は「間違えないためのガードレール」、フィールは「どう気持ちいいかの主語」
- 入力体験そのものが「自分のサーフィンを言語化する」価値を持つようにする
- 個人利用前提。蒸留方式により元記事の再配布は構造上発生しない
